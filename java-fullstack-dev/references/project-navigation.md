# 大型项目与 AI 知识库导航

有些团队把业务文档、迭代材料和代码放在不同仓库。先找到入口与版本关系，再按任务选读。这个方法来自对多个本机工作区的定向梳理；目录名称仅是示意，不要求新项目照搬。

## 先画一张“资料从哪里来”的小地图

| 资料层 | 常见入口 | 当前任务要拿到什么 |
| --- | --- | --- |
| 项目规则 | `AGENTS.md`、团队 README、工程规范 | 禁止事项、构建/测试门禁、代码风格 |
| 业务语言 | 术语表、领域索引、状态机 | 名词、状态含义、谁能做什么 |
| 架构 | 服务目录、模块地图、调用拓扑 | 请求落在哪个仓库/模块、上下游是谁 |
| 数据与接口 | 数据模型、API 清单、DTO、迁移 | 字段含义、关系、兼容约束 |
| 本次变更 | PRD、技术方案、任务清单、已有 PR | 验收条件、范围、未决问题 |
| 行为证据 | 当前分支源码、测试、运行日志 | 现行实现与实际结果 |

只读与当前任务相关的部分：主模块深读，直接依赖模块查接口和数据契约，其他模块用索引定位。若知识库有 `module-function` / `module-api` 一类分层文件，先读摘要，再按需要查完整契约；跨系统接口要核对完整请求、响应和错误语义。

## 防止“文档看着对，代码却不是这版”

1. 分别记录代码仓、知识库仓的分支与提交，以及文档最后更新时间。Git submodule 还要看当前固定提交；不要默默 `pull` 或更新子模块。
2. 检查文档链接是否真实存在；路径失效时搜索当前仓库，不把旧目录硬套进新代码。
3. 对关键结论回源码验证：路由和 HTTP 方法、DTO 字段、枚举/状态值、权限常量、SQL 条件、锁与事务位置。即使文档写了“必须”，也要观察同一模块当前代码和团队现行规则；旧规范可能与代码不一致。代码也可能有 Bug，因此“代码当前这样做”不等于“需求应该这样做”。
4. 冲突记录为：文档版本/语句 → 当前代码位置/行为 → 影响 → 待负责人确认的问题。先完成不依赖该问题的工作。

## 任务完成后留下可维护的知识

如团队维护知识库，用本次 diff 与测试结果检查是否应更新模块摘要、API 清单、数据模型或术语。只改真正变化的条目，标注代码提交与生效版本；不要重写整个旧文档。业务规则的取舍仍由产品/负责人确认。公司项目事实应写在其私有文档，不进入这个公开 Skill。

# Java 后端改动卡：按真实任务选择

这些是改动前的关键问题，不要求简单任务逐项填表。先从同模块相邻实现取得项目写法，再用当前需求的验收标准决定覆盖范围。对应定位方法见[调用链实操](code-tracing.md)。

## 新增或修改接口

1. **契约**：HTTP 方法、路径、必填字段、空值、枚举、时间和金额精度；旧调用方是否继续可用。确认接口文档、Controller 注解、DTO 校验与前端消费一致。
2. **入口**：认证、功能权限、对象权限或租户范围在哪里执行。列表过滤与详情、更新、导出是不同路径，逐个核对。前端按钮控制不是后端授权。
3. **业务**：Service 是否把无效状态、重复操作、并发修改处理清楚。新逻辑放在哪个业务边界，是否需要给下游发送事件或清缓存。
4. **响应**：异常在哪里转换成业务错误，前端能否正确展示；错误码和 HTTP 状态是否符合项目约定。日志记录可关联 ID，不输出凭据或敏感数据。
5. **验证**：至少覆盖一条成功、一条参数错误、一条无权或跨数据范围路径，以及本次逻辑最关键的边界。

## 改数据库字段或查询

| 场景 | 必查项 |
| --- | --- |
| 新增字段 | 是否可空、默认值、历史数据回填、DTO/Entity/Mapper/前端映射、导入导出、迁移与回滚 |
| 修改查询 | 分页与排序稳定性、索引、租户/数据范围、软删除、自定义 SQL 条件与参数绑定 |
| 修改状态 | 旧状态记录、状态机允许的迁移、并发更新条件、下游消费和报表口径 |
| 修改唯一性 | 数据库唯一约束与已有重复数据、并发下“先查再写”的竞态、错误提示 |

用项目已有的 Flyway、Liquibase、SQL 脚本或平台流程处理 Schema；不要因为本地实体类变了就直接更新共享库。SQL 变更在隔离数据中验证执行结果，必要时看执行计划。迁移和代码发布先后取决于兼容策略，需结合实际部署流程。

## 批量导入、导出或异步任务

- 导入：文件大小、行数、格式、重复行、字典值、全部失败还是部分成功；每行错误如何回给用户。
- 写入：是否先全量校验、批次大小、事务范围、重复提交、并发导入和失败重试。`@Transactional` 只覆盖其生效的事务资源，不能自动回滚远程调用或消息。
- 导出：查询权限与列表一致吗？大数据量是否分页/流式处理？字段脱敏、编码和时间格式是否与前端一致？
- 异步：任务状态、重试、幂等、超时和可观测性；线程上下文中的用户身份或 Trace 是否会丢失。

验证时用包含合法行、非法行和重复行的小样本；再按项目允许的测试方式核对批量边界。不要把上传成功或返回任务 ID 等同于数据处理成功。

## Spring / Java 运行时的四个常见误判

1. **事务注解存在 ≠ 一定生效。** 看方法可见性、代理调用、自调用、异常类型、事务管理器和异步边界；核对当前 Spring 版本的实际规则。
2. **编译通过 ≠ 契约正确。** JSON 字段、空值、日期、枚举、分页包装与错误响应需要前后端或契约测试。
3. **集合操作正确 ≠ 并发正确。** 靠内存判断、`synchronized` 或“先查再写”不能天然覆盖多实例；按业务选数据库约束、版本号或幂等键。
4. **框架自动处理 ≠ 自定义 SQL 自动处理。** 软删除、租户、权限、审计字段和乐观锁均需检查当前项目的插件配置与最终 SQL。

完成后把“改动文件 → 影响接口/表/消息 → 验证命令及结果 → 未覆盖风险”写进 PR。若项目有额外门禁，以项目要求为准。

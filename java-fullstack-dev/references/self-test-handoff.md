# 自测、PR 与提测交接

这份清单用于把“我本地能跑”变成测试同事能独立接手的结果。具体测试、分支和发布门禁以新项目规则为准；只对本次改动有影响的项目逐项核对。

## 从验收标准生成自测矩阵

| 场景 | 最小验证层 | 需要观察的结果 |
| --- | --- | --- |
| 业务规则/计算/状态 | 单元测试或服务级测试 | 正常、边界、错误输入与状态不变量 |
| 请求/响应契约 | Controller/API/契约测试 | 字段、校验、错误码、序列化和旧调用方 |
| DB/事务 | 隔离数据库集成测试 | 写入、唯一性、查询条件、回滚与历史数据 |
| 权限 | 后端接口加受限登录态 | 功能权限、对象/租户范围，含详情/导出/写入 |
| 异步/跨服务 | 受控集成或测试环境链路 | 消息/下游结果、超时重试、重复和失败恢复 |
| 用户流程 | 浏览器或人工走查 | 页面操作、网络请求与业务结果一致 |

UI 用例证明用户交互；API 用例覆盖规则组合；单元测试覆盖纯逻辑。不是每个需求都要把同一排列组合在三层重复跑。测试用例需有独立预期来源，不能仅按当前实现写“应该如此”。如果目标工作区装有 `test-case`、`generate-pytest`、`qa` 等 Skill，先检查它们的实际能力、依赖和项目适用性，再用来补充相应层；不把它们当成任何新公司的默认工具。

## 自测执行记录

1. 从需求/技术方案列出本次变化的用户行为与失败路径；补上[审查](review-before-test.md)发现的高风险面。
2. 运行仓库指定的 lint、相关模块测试和必要构建；记录**实际命令、环境、退出码及失败**。只改前端就选前端验证；跨模块改动按影响扩大范围。测试必须在隔离数据或团队许可环境执行。
3. 用同一次请求把页面、API、后端日志和可观察数据结果关联起来。验证导入/导出时核对文件内容和业务记录，不只看响应成功。
4. 缺少环境、测试账号或下游时，把已验证层与未验证层分开；没有跑的写 `not run`，不能填 PASS。
5. 修复后按新代码提交重新验证原失败路径和受影响回归；旧证据不能冒充新版本验证。

## PR 描述与提测说明

```md
需求与目标：<需求链接、验收点>
代码范围：<仓库、分支/提交、前后端/数据库/配置改动>
调用链与影响：<页面/API、服务、表/消息/下游>
接口变化：<新增/变更路径、字段、兼容性，链接到实际接口文档>
自测：<命令、环境、时间、场景、结果与证据>
已知限制：<未验证项、风险、测试数据准备与回收>
提测环境：<经核实的部署版本/镜像、入口与目标配置>
建议测试重点：<高风险路径、权限、边界、上下游>
回退与负责人：<按项目流程填写>
```

目标是让测试同事无需再追问“哪个分支、哪个环境、从哪里开始测”。提测版本需核对实际部署代码与提交；PR 已合并、CI 通过或服务 Ready 不能单独证明测试环境已有该功能。涉及发布或数据库变更时，遵循新团队审批与操作分工。

# 入职后拿到任务：直接开工

本页用于你已经收到需求或 Bug、需要尽快交付的场景。目标是用 AI 加速定位和实现，同时让团队能评审、能复现。不要先做完整知识库，也不要求先学完 Java。

## 第一次打开仓库，15–30 分钟建立工作基线

把仓库交给 AI，先让它只读检查 `AGENTS.md`、README、构建文件、配置模板和目标模块；有独立知识库时先看其索引。要求它回答：当前分支是否有未提交改动、代码与文档是否在同一基线、JDK/Spring/构建工具版本、如何运行相关测试、目标服务的启动入口、外部依赖指向何处。缺少信息就标记待确认；不要编造启动命令或擅自连接共享环境。

如果任务已经明确，优先按[调用链实操](code-tracing.md)追任务入口，不必穷尽全仓库。把同事给出的业务背景、接口文档和验收标准放在**公司允许的工具和私有文档**中。项目画像只填写完成当前任务必需的内容；需要交接时可复制 [任务工作单](../assets/TASK_BRIEF.template.md) 到私有位置记录本次任务。

## 每个任务都按这条短流程推进

1. **对齐结果**：把需求变成可验证的行为，明确输入、输出、失败和边界；业务不清楚的点集中问负责人。
2. **定位现状**：按知识索引找目标模块，再查前端入口、API、Controller、Service、Mapper/Repository、表和测试；确认相邻功能的写法。文档给意图，代码给当前行为。旧文档的路径、状态值和接口字段需回源码核实。
3. **列改动点**：说明要改哪些文件、API/数据兼容性、权限、事务、幂等或迁移风险。简单任务用简短最小方案后直接做；新增抽象/依赖/表/服务或跨服务变更时，用 `java-change-review` 核对是否有当前需求证据，再按团队门禁确认方案。
4. **实现和验证**：按[后端改动卡](backend-changes.md)选择与本次改动相关的检查点，做最小改动，运行项目要求的 lint/测试；在隔离数据上验证正常、错误、重复或无权路径。联调时用同一次请求关联页面、接口和日志。Bug 任务用[排障卡](bug-fixing.md)固定失败证据与根因。
5. **交付**：用 `java-change-review` 审本次明确的 diff 与回归面；PR 写清改动、验证命令及结果、未覆盖项、风险。收到 CR 后按证据修正，不把“编译成功”当作业务完成。

## 直接可用的对话指令

**接新需求**

```text
请使用 java-fullstack-dev 帮我完成这个需求：<粘贴需求与验收标准>。
先只读定位当前实现和最相近的功能，列出前端到数据库/外部服务的调用链、需要改的文件、未知的业务规则与风险。信息足够后直接做最小实现并运行相关测试。请区分已验证事实和推断。
```

**修 Bug**

```text
请使用 java-fullstack-dev 定位并修复这个问题：<现象、环境、复现步骤、期望、实际、请求 ID/错误日志>。
先复现并缩小到具体代码与数据条件，给出根因证据；加能证明修复的测试，再改代码并验证。若无法复现，明确缺少哪项证据，不把猜测写成结论。
```

**看不懂一段 Java 代码**

```text
请结合当前仓库解释 <类/方法/文件> 在本次需求里的作用：谁调用它、输入输出、事务/异常/副作用、对应前端表现。只解释我完成任务所需的 Java 概念，并指出需要回源码验证的地方。
```

**提交前自查**

```text
请使用 java-fullstack-dev 评审我当前 diff。重点看业务验收、前后端契约、鉴权/数据权限、事务、并发、SQL、测试遗漏和无关改动。只报告有代码证据且可操作的问题，附文件与行号。
```

## 需要同事尽快给出的最少信息

- 本次任务的验收标准、负责答疑的人和目标分支。
- 项目固定的 JDK/构建命令、测试门禁与本地运行方式。
- 本机服务会连接哪些共享系统，以及可用的安全测试数据。
- 数据库变更、环境发布、权限配置由谁操作，何时需要审批。

有其中一项暂时拿不到时，继续做不依赖它的定位与本地代码工作，并把阻塞点写清楚。

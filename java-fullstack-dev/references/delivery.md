# 功能交付与代码评审

这是一份按任务取用的检查表。项目自身规范、实际依赖和业务规则优先；简单改动无需机械填写全部项目。

## 改动前：从需求到调用链

1. 写清用户操作、请求和预期结果，列出正常、失败、重复与并发场景。业务文档记录意图，源码和实际运行记录当前行为；冲突处标“待确认”。
2. 搜索页面调用与后端路由，追踪 `Controller → DTO/校验/鉴权 → Service/事务 → Mapper/Repository → DB/外部依赖`。记录数据的状态变化、缓存或消息副作用。若项目有 BFF、Feign 或事件消费者，把它们也放进链路；跨仓改动使用[多服务变更表](cross-service.md)。
3. 在既有模块里找一个相近实现与测试。确认团队的响应、异常、日志、命名、注入、ORM、迁移和权限约定；不要从别的项目复制专有基类与注解。
4. 只在必要时做技术设计：对跨服务调用、状态机、数据库变更、幂等、并发和回滚，写出边界与失败恢复方式。

## 实现时：后端重点

| 主题 | 要核对的事实 |
| --- | --- |
| API 契约 | 请求字段的必填、空值、长度、时间/时区、枚举；响应与错误码是否兼容调用方 |
| 权限 | 身份认证、功能权限、对象/租户/数据范围是否在后端校验；读写路径分别验证 |
| 事务 | 哪些 DB 写入必须一起提交；外部 HTTP/MQ/缓存是否超出事务；异常和代理调用会如何影响回滚 |
| 数据 | 唯一约束、索引、软删除、自定义 SQL、分页排序、批量量级、迁移和历史数据兼容 |
| 幂等与并发 | 重试、重复点击、消息重投、并发更新如何防止重复副作用；锁/版本/唯一键的适用范围 |
| 批量处理 | 输入上限、全量报错还是快速失败、循环查库/N+1、部分成功还是整批回滚、成功数量语义 |
| 观测 | 关键 ID、Trace、失败原因可定位；日志不包含密码、Token、个人敏感数据 |

`@Transactional` 默认回滚规则随 Spring 配置与版本核对；通常 unchecked 异常触发回滚，checked 异常需显式规则。自调用和异步调用可能绕过预期事务代理。不要因为方法上有注解就认定事务生效。若使用 MyBatis-Plus 逻辑删除，内置操作与手写 XML SQL 分开检查实际条件。

## 验证：按风险选最小充分组合

- 纯逻辑：单元测试覆盖正常、边界和异常。
- Controller/契约：验证校验、权限、错误响应、序列化与前端消费方式。
- 持久化：在隔离的测试数据库核对 SQL、唯一约束、事务回滚、软删除及分页。
- 跨服务或消息：验证超时、重试、重复投递和失败恢复；必要时做契约或集成测试。
- 前后端联调：同一请求关联页面、网络请求和后端日志；确认字段、错误提示与权限行为。

`./mvnw -pl <module> -am test` 只是 Maven 示例；先看仓库是否用 Maven、模块名与团队测试门禁。不要在共享环境直接跑会清理或修改数据的测试。报告明确写“执行了什么”和“没覆盖什么”。

## PR / CR 可复用摘要

```md
目标：<用户行为与业务规则>
范围：<前端、后端、数据或配置的实际改动>
关键决策：<权限、事务、幂等、兼容性>
验证：<命令、环境、结果；未验证项>
风险与回退：<真实风险、可操作的回退路径>
待团队确认：<尚无证据的假设>
```

评审时按证据提问：哪一段代码校验对象权限？重复请求会写几次？异常出现在哪一步，哪些数据已提交？自定义 SQL 是否包含项目要求的隔离和软删除条件？日志能否定位失败且不泄露敏感信息？

当本次功能是旧功能的变体时，列出两者在输入、状态、权限、事务、下游副作用和响应上的差异，避免只复制表面代码。交付后若团队维护模块知识库，再用实际 diff 检查文档是否需要局部更新。

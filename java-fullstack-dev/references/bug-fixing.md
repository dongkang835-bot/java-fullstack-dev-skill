# Java 全栈 Bug 排障卡

先把现象缩成一条可复现的请求：环境、时间、用户角色、操作、请求参数或样例数据、预期与实际、请求 ID/Trace、错误日志。日志和截图来自不同时间时分别标明，不拼成一次执行证据。

## 用症状决定先查哪里

| 现象 | 第一批证据 | 常见下一跳 |
| --- | --- | --- |
| 页面没请求 | 按钮状态、路由守卫、浏览器 Console、Network | 前端事件绑定、权限显隐、表单校验 |
| 401 / 403 | 同一登录态的 Network、后端鉴权日志 | Token/Profile、功能权限、对象/数据范围；不要只看按钮 |
| 400 / 参数错误 | 请求体、DTO 校验、异常映射 | 字段名、类型、空值、时间格式、接口版本 |
| 500 / 超时 | 请求 ID、服务日志、下游调用耗时 | 异常根因、Feign/HTTP、DB 锁、线程池、重试 |
| 返回成功但数据不对 | 响应、查询条件、写入日志、隔离库数据 | 事务、缓存、状态机、异步任务、软删除或权限过滤 |
| 偶发/重复数据 | 并发时间线、重试日志、唯一约束 | 幂等、并发更新、消息重投、任务重复触发 |

## 一次排障的执行顺序

1. **确认基线。** 记录哪个环境、哪个服务实例、代码提交/镜像，以及是否与报告发生时相同。当前观察不能自动代表历史现场。
2. **复现并关联。** 页面、Network、后端日志使用同一次请求 ID/业务 ID；没有 ID 时用时间窗、用户与关键参数缩小，注意脱敏。
3. **定位首个错误点。** 追 `Caused by`、被包装的业务异常与下游响应；异常出现的位置不一定是根因。对超时画调用时间线，对数据错误对照读写 SQL 条件。
4. **提出可证伪假设。** 例如“只在旧记录缺少字段时失败”，找能区分它和其他原因的样本；不要直接改最显眼的报错行。
5. **先固定失败证据，再修复。** 能写自动化测试时用最小数据复现；不能稳定自动化时保留受控手工步骤和实际响应。
6. **验证修复与回归。** 检查原失败路径、正常路径、相邻业务、重复请求/失败恢复；说明测试环境与未验证项。

## 调试命令范例

```sh
rg -n '错误码|异常类名|请求路径|业务方法名' --glob '*.{java,xml,js,ts,vue}'
rg -n 'throw new|@ExceptionHandler|@ControllerAdvice|@Transactional' --glob '*.java'
rg -n 'timeout|retry|fallback|@FeignClient' --glob '*.{java,yml,yaml,properties}'
```

先按项目目录缩小范围；日志平台、数据库和远程环境由该项目权限与规则决定。不要在共享环境运行会写数据的“复现脚本”。

## 交付给同事的缺陷结论

```md
现象与影响：<谁在什么条件下受影响>
复现条件：<环境、版本、步骤、样例数据；数据脱敏>
根因证据：<具体代码/日志/请求，说明为何能解释现象>
修复：<改动与不变量>
验证：<原失败路径、正常路径、边界；命令/环境/结果>
剩余风险：<未覆盖或依赖外部条件的部分>
```

根因未证实时写“待核实”，给出下一条最有区分力的证据需求。不要把“重启后好了”直接写成根因。

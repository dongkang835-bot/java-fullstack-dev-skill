# 开发自审与提测前代码审查

本页是开发者的快速自查卡。需要完整的方案边界审查、Git 范围冻结与代码问题确认时，使用同包 `java-change-review`。若目标环境还安装了更完整的 `code-review-test`，则在团队允许的仓库中**按它自身的 SKILL.md**执行测试视角审查；本包没有复制其脚本、内部配置或业务规则。

## 先固定审查范围

记录仓库路径、目标分支/提交、比较基线、工作区是否包含 staged/unstaged/untracked。多仓库分别记录，不能把主仓和子模块混成一个 diff。基线不明时先确认 PR/MR 的真实目标，不默默用 `main`/`master`。历史提交审查用对应 SHA 的源码与依赖，不能拿当前 HEAD 的代码解释旧行为。

```md
仓库：
基线 SHA → 目标 SHA：
包含的工作区改动：
需求/技术方案版本：
未纳入的仓库或文件：
```

## 四轮检查

1. **逐处读改动。** 不只看 diff 行，打开完整方法/类；检查条件、空值、删除的 guard、异常、日志和返回值。
2. **追有限影响面。** 对变更的 API、DTO、字段、枚举、公共方法、SQL、事件，找直接调用者、实现类、生产者/消费者和相关测试；记录搜索边界。多态、动态路由、反射、消息订阅可能无法穷尽，写入剩余风险。
3. **尝试证伪问题。** 找同层校验、前置权限、feature flag、异常处理、旧数据约束和反例；与当前需求核对。只把本次引入的问题或同一修复面漏改的等价入口作为候选，不顺手把无关旧问题都归咎于本次 PR。
4. **用真实验证确认。** 最小定向测试或受控复现应断言业务结果；编译、静态扫描或 Mock 自身通过不能代替真实功能。无法执行时标“待验证”，说明缺哪一个环境、数据或入口条件。

## Java/全栈优先风险

| 风险 | 要找的证据 |
| --- | --- |
| 前后端契约 | 方法/路径、字段、空值、枚举、分页、下载、错误提示；同版本的消费方 |
| 授权 | 功能权限与对象/租户/数据权限；列表、详情、写入、导出分别核对 |
| 状态与事务 | 状态机、并发更新、回滚条件、远程副作用、重复请求/消息 |
| 数据与查询 | 迁移、历史值、唯一约束、索引、软删除、自定义 SQL 的实际条件 |
| 运行时 | 线程池、超时/重试、N+1、批量大小、缓存一致性 |

## 审查输出

```md
范围：<仓库、base/target、需求版本>
已检查：<改动点、调用/数据面、执行的测试>
确认的问题：<文件行号、触发条件、可观察错误、反例检查、最小修复>
待验证的疑点：<为什么尚未确认，需要哪条证据>
回归范围：<用户操作/API、上游/下游、数据与权限场景>
剩余风险：<未穷尽的调用面、未运行的环境/测试>
```

若新工作区安装 `code-review-test`，把当前任务的仓库、明确 base/target 或 PR/MR、需求文档和期望阶段交给它。该 Skill 是**测试视角**，会进一步形成上下游回归范围；它的动态验证、缺陷提报和证据门槛由其自身规则控制。开发自审仍应先完成，不把调用另一个 Skill 等同于代码已通过人工评审。

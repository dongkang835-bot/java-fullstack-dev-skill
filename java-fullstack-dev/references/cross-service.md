# 多服务变更：先确定契约和边界

当一个需求影响两个以上服务、仓库，或改变 API/事件的生产与消费关系时，先做一页影响分析，再分仓实施。这是为了避免只改页面和一个 Controller，却漏掉下游状态、权限或兼容性。

## 最小影响表

| 组件/仓库 | 入口或角色 | API/事件/数据变化 | 依赖的其他改动 | 验证方式 |
| --- | --- | --- | --- | --- |
| 前端 | 用户入口 | 待填 | 待填 | 页面 + 网络请求 |
| BFF / API | 对外契约 | 待填 | 待填 | 契约/权限测试 |
| 业务服务 | 状态与事务 | 待填 | 待填 | 单测/集成测试 |
| 下游/消息消费者 | 副作用 | 待填 | 待填 | 重复与失败场景 |

对每条调用写清提供方、调用方、HTTP/事件字段、成功与错误语义、超时/重试、幂等、权限和兼容策略。新增字段是否可选、旧消费者能否忽略、枚举变化会否破坏旧逻辑，都要结合实际序列化与消费者代码验证；不要把“只增不改”当成万能法则。

## 实施与联调

1. 先核对各服务职责与现有同类契约，再确认需要变更的仓库。必要时由团队评审接口和事件契约。
2. 按依赖拆任务：独立部分可并行；有依赖的先提供可联调契约或 Mock。每个仓库分别记录分支、测试和 PR。
3. 联调覆盖正常、失败、超时、重复请求/消息、部分成功和恢复。对跨事务边界的副作用说明补偿或重试策略。
4. 发布顺序取决于兼容策略与现有部署方式；只给出经过验证的顺序和回退方案，实际发布遵循团队授权与审批。

若只是单仓、单服务的小改动，直接使用[交付指南](delivery.md)，不需要制造多服务文档。

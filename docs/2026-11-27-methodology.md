# 2026-11-27 优化沉淀：从新手开工到可评审交付

## 目标与实际变化

昨天的仓库提交形成三段衔接：`java-project-onboarding` 先核实工作站、仓库和运行基线；`java-fullstack-dev` 用一个真实需求或 Bug 追通前端、Java、数据和外部服务，完成最小改动；`java-change-review` 在编码前控制方案复杂度，在交付前审明确的 Git 范围。提交还补充了任务工作单、项目画像、只读盘点脚本和按场景阅读的参考页。

这个体系要解决的是：纯小白无需先学完开发，也能借助 AI 写出资深前后端工程师水准的代码。这里的“资深水平”要落在可观察的结果上：业务规则有来源；调用链和数据边界追到位；实现与现有系统一致且不过度设计；测试能证明关键行为；未验证处明确留下。现有材料原本分散覆盖这些点，本次新增[资深质量闭环](../java-fullstack-dev/references/senior-delivery.md)，让 AI 在每个任务中把“验收 → 不变量 → 改动 → 证据 → 反向审查”连起来。

## 从实战分享 Prompt 提炼的执行方法

本次进一步核对了 "参考文档" 中后端技术方案、代码生成、代码 CR，以及前端方案、开发与复审的提示词。它们提升效果的关键，是把 AI 的输入和动作写实：给出当前迭代/分支/需求/模块变量；按目的读取领域、架构、数据、相邻代码；从 PRD 推导技术决策与待确认项；按方案修改代码；用针对性清单反查权限、事务、并发、性能和前后端契约。前端部分还强调先找同类组件、核对通用组件的旧调用方、再联调真实接口。

这些方法已改写为可复制的[分阶段 Prompt](../java-fullstack-dev/references/prompt-playbook.md)。保留“具体上下文 + 明确输出 + 自检回路”的结构；原文中的固定技术栈、项目目录、权限常量、锁 Key、注解和业务状态仍属于原项目。技术方案里的锁设计、待确认问题和文件清单都按本次风险与证据决定，不机械要求每项都有。

本次再次对照 "参考文档" 的前后端章节，补齐了此前容易漏掉的三段：前端依据需求、后端契约和测试用例单独形成技术方案；把评审确认的接口、权限和边界回写方案；开发后针对页面状态、共享组件旧调用方和真实接口持续做 CR 与修复。后端 CR 增补了异常回滚、多锁顺序与乐观更新受影响行数的条件检查。对应内容均以通用角色系统提示词和可复制的任务提示词呈现。

## 用真实项目代码校准 Prompt

本次只读检查了 "目标项目" 的前端、后端和知识库各自的代码版本，并从一个页面入口追到共享组件、后端接口、校验、查询和写入调用。这个样本说明 Prompt 需要引导 AI 追真实调用链：页面权限和服务端数据权限处于不同层；共享组件展示的结果依赖真实响应；方法覆盖与事务边界可能影响运行行为；外部副作用也要继续追。历史方案中的字段与当前源码可能不同，不能直接用旧文档推断现行接口。

因此在 Prompt 中补了三项可执行动作：分别固定知识库与代码版本；参考相邻实现时追到真实入口和副作用，不把它视为正确性证明；前端按同版本后端契约核对响应字段与错误语义。这次是源码静态核对，没有运行 "目标项目" 的服务或测试，不宣称完成端到端验证。项目专有的类名、权限标识和业务规则只保存在该项目允许的私有位置。

## 三个 Skill 各自提供什么

| 时点 | Skill | 要交付的真实成果 |
| --- | --- | --- |
| 第一天或新项目 | `java-project-onboarding` | 已核实的版本、依赖与最小启动结果；私有项目画像和未知项 |
| 需求或 Bug | `java-fullstack-dev` | 源码与运行证据支撑的调用链、最小实现、针对风险的验证、可解释的交接 |
| 方案复杂或准备提测 | `java-change-review` | 明确 SHA/diff 范围、现有保护和反例检查、确认问题与回归面 |

这不是固定的三次仪式。环境已知时直接做需求；简单改动用短方案和定向验证；只有复杂度和风险上升时才展开完整设计与审查。

## 从私有测试审查 Skill 提炼的通用精华

某些 "项目私有测试审查 Skill" 包含专用的流程、环境、证据格式、平台扩展和提报权限。本公开仓库只提炼可以跨项目复用的决策方法，落在 `java-change-review` 与质量闭环中：

1. **先固定被审对象**：每个仓库独立确认 base、target、工作区范围和目标版本；历史问题要看当时的源码快照。
2. **候选先证伪**：读完整上下文与上游保护，证明合法输入可达、问题由本次变更引入或同一修复遗漏，并写出可观察后果。
3. **执行证据有边界**：定向测试或受控复现要断言业务结果；Mock、编译和静态推理分别说明能证明什么，不能冒充真实链路通过。
4. **回归追上下游**：由改变的入口、字段、状态、SQL 或事件追直接调用者和消费者，按风险选最小充分测试；搜索未穷尽时写覆盖缺口。
5. **状态分开记录**：已确认问题、待核实疑点、测试未执行、缺陷已提报和发布已完成是不同事实。外部写入与提报仍需目标项目的授权。

这些是方法，不复制私有 Skill 的源码、内部路径、业务规则、报告契约或自动化脚本；也不把它的特定门槛变成所有项目的标准。公开 Skill 可独立审查，安装了私有扩展且适用于目标项目时再按其自身说明衔接。

## 给新手的一条实际用法

```text
请使用 java-fullstack-dev 完成下面的需求或 Bug：<原始描述与验收标准>。
先读取当前项目规则、代码基线和最相近的实现；从用户入口追到后端数据与下游。
把每条验收连到业务不变量、最小改动和能观察业务结果的验证。
规则不明且会改变方案时明确提出问题，其余部分继续完成。
实现后运行相关验证，再对本次 diff 找反例，报告实际通过、未执行和剩余风险。
最后用我能复述的语言解释最关键的代码决策。
```

下一次真实项目任务应检验这套方法是否有效：看 AI 是否准确找到已有路径、提出真正改变方案的业务问题、实现最小改动、运行有业务断言的测试，以及是否诚实说明证据边界。未经过真实任务检验前，不宣称它已经稳定产出资深工程师水平的代码。

# 技术方案边界审查：防止过度设计

审查对象可以是一页方案、AI 的实施计划，或准备编码前的口头需求。先把“这次必须交付的用户行为”与“以后可能需要”分开；项目自带的设计评审流程仍优先。

## 方案应回答的六件事

1. **验收**：谁在什么状态下做什么，成功/失败/重复操作有什么可观察结果？需求未定的地方标待确认，不用抽象层填补业务空白。
2. **现状**：相邻功能在哪些仓库/模块？已有接口、Service、Mapper、组件和测试能复用什么？引用当前分支文件位置。
3. **最小改动**：文件/接口/表/配置变更清单，数据流和事务边界。说明为什么放在该层；用户看不到、测试也无法证明的附加功能先不做。
4. **风险**：权限、数据范围、兼容、历史数据、并发、幂等、下游、迁移和回退。没有触及的项可写不适用，不机械扩成“大架构”。
5. **验证**：哪一个最小测试证明每项验收？哪些需要隔离 DB、真实接口或人工走查？
6. **方案选择**：至少比较“复用现有路径的最小方案”和 AI 提出的新抽象；只有在当前需求带来明确收益时增加复杂度。

## 复杂度账本

| AI 建议新增 | 保留前需要的证据 |
| --- | --- |
| 新服务/模块/微服务 | 现有边界为何不能承载；独立部署、数据所有权或吞吐需求是什么 |
| 通用框架、插件、策略模式 | 眼前有几个真实变体；现有简单分支为何难以维护 |
| 新表、消息、缓存 | 明确的数据量/一致性/性能目标、迁移与失败恢复方案 |
| 新依赖/基础设施 | 项目是否已有等价能力；版本、许可、运维与安全成本 |
| 大范围重构 | 当前需求为何无法局部实现；回归范围和回退如何控制 |
| “预留未来扩展” | 已确认的后续需求、契约和时间；否则作为后续事项 |

不是一律禁止新增：当代码证据表明现有路径会破坏边界或重复风险高时，明确写出新增复杂度的收益、替代方案和验证方法。不要为了“优雅”重命名无关模块、重写整层 Mapper 或改动没有触及的公共基类。

## 按风险决定文档长度

- **局部低风险**：一段“验收 → 当前实现 → 改动文件 → 测试”即可，不强制画架构图。
- **跨前后端或单服务数据变更**：一页接口/字段/权限/事务/测试表。
- **跨服务、Schema、状态机、异步副作用或高风险兼容**：完整技术方案，包含调用图、数据迁移、失败恢复、发布和回退；按项目评审门禁走。

## 输出模板

```md
本次必须满足：<验收点>
现有路径：<文件/行号与可复用实现>
建议最小方案：<改动点、数据流、测试>
建议删去/推迟：<新增复杂度及缺少的当前需求证据>
必须保留的风险控制：<权限/事务/兼容/回退>
待业务或架构负责人确认：<确实改变方案的问题>
```

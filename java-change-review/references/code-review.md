# 代码审查：范围、反证、确认、回归

## 先确定被审内容

运行 `review_scope.py` 得到仓库、比较方式、base/target SHA、变更文件和工作区状态。工具不读取 PR/MR 平台，若用户给 URL，应先从可用 provider 核对真实 base/head 与提交历史，再在本地固定范围。范围不明时先做可确认的只读分析，不给“本次没有问题”的结论。

对每个仓库单独审查；主仓的子模块指针变化与子仓源码变化都要记录。工作区模式包含 staged、unstaged、untracked 名称；未跟踪文件需按任务相关性单独打开。二进制、生成物或未覆盖路径写入报告。

## 逐处审查的检查面

| 面 | 要核对的证据 |
| --- | --- |
| 逻辑与边界 | 改动所在完整函数、前置 guard、空值、错误分支、状态转换、异常映射 |
| 被删保护 | 旧校验、权限、锁、幂等、回滚、资源释放是否有等价替代 |
| 前后端契约 | 路由、DTO/VO、枚举、序列化、错误码、导入/导出、旧消费方 |
| 数据与中间件 | SQL 条件、迁移、历史数据、事务、缓存、消息重试、外部副作用 |
| 运行成本 | N+1、循环网络调用、无界批量、线程池/连接/文件释放，有实际规模证据 |
| 项目规则 | 适用的 `AGENTS.md`、编码/测试规范与当前模块习惯；文档冲突需说明 |
| 不完整修复 | 与 changed path 语义等价、仍可达的另一入口是否漏改 |

对变更的 API、公共方法、字段、状态或事件，有限地找 caller、implementation、producer、consumer、Mapper/SQL 与测试。可用 `rg`/`git grep`，有图工具时只作候选，回目标 SHA 源码核实。不能仅凭同名方法或空搜索结果断言影响面完整。

## 候选问题必须过四问

1. **这是本次引入或本次修复遗漏的吗？** 比较 base 与 target；存量问题不冒充新增回归。
2. **路径真实可达吗？** 给合法输入/状态、权限与 feature flag 条件，证明会走到疑点。
3. **已有保护在哪里？** 查上游校验、同层 guard、异常处理、数据库约束和消费者容错，主动寻找反例。
4. **结果可观察吗？** 是错误数据、越权、异常、丢失副作用或可测性能退化；能用定向测试或受控复现就执行并记录结果。

无法回答时列“待验证疑点”，不要写正式缺陷。对未修改的等价入口，只有能证明相同业务契约、当前仍可达、遗漏同一修复不变量时，才报告“不完整修复”。

## 交付格式

```md
范围：<仓库、比较模式、base/target SHA、未跟踪文件与排除项>
需求/方案：<版本及关键验收；缺失则写缺失>
确认问题：<严重度、变更锚点、合法触发条件、路径、结果、反证、最小修复>
待验证疑点：<缺少的证据与下一步>
验证：<命令、环境、退出码、业务断言、证明边界>
回归：<前端入口、API、数据、权限、下游；优先级和理由>
剩余风险：<动态调用/未执行环境/未覆盖仓库>
```

如果没有经证实的问题，写“在上述范围与验证条件内未发现可确认问题”，并保留未覆盖项。审查不会自动提交缺陷、评论 PR、推送或发布；这些动作按用户请求与项目权限另行处理。

# Java 全栈方案与变更审查

用于需求实现前的方案审查、开发中的复杂度控制、提交前 CR 和提测前回归分析。先读当前项目 `AGENTS.md`、需求、技术方案与适用规范；项目规则优先。不要把“写了很多代码”“用了新框架”本身当问题，要证明它比当前需求所需的方案增加了具体维护、兼容或运行风险。

## 选择审查入口

- **还没写代码或技术方案待审**：按[方案边界审查](references/design-gate.md)核对验收标准、现有实现、最小方案和复杂度成本。简单改动给简短改动说明；只有跨服务、数据结构、状态机、权限或高风险发布需要更完整的技术方案。项目若有强制设计门禁则遵循项目。
- **已有 diff/PR/commit**：先用 `python3 scripts/review_scope.py --repo <绝对仓库路径> --base <已核实基线> --head <目标>` 固定范围；PR 语义需要 merge-base 时加 `--merge-base`。仅审工作区用 `--worktree`；单提交用 `--commit`。脚本只读，不 fetch，不默认猜 main/master，结果放私有位置。随后按[代码审查](references/code-review.md)逐处核查。
- **准备提测**：在代码审查基础上形成“影响入口 → 最小自测 → 测试重点 → 未验证项”，交给 `java-fullstack-dev` 的自测与提测流程。缺需求或设计文档时继续能独立核查的代码范围，标出缺口。

## 审查原则

1. 先冻结每个 Git 仓库和 SHA，再读 diff；嵌套仓库、子模块分别审。历史变更用对应快照，不以当前 HEAD 代替。
2. 逐处打开完整方法/类，找调用者、实现类、生产者/消费者、SQL/配置和相关测试。对动态边界写明覆盖缺口。
3. 候选问题先找反例与已有保护，再给出触发输入、执行路径、可观察错误和最小修复。区分“已验证问题”“待验证疑点”“无本次相关问题”；不把无关旧问题塞进本次 CR。
4. 对 AI 方案特别检查：能否在现有模块完成、是否引入新依赖/抽象/表/服务、是否增加迁移与运维成本、是否超出当前验收。只有具体收益和风险证据才能保留新增复杂度。
5. 报告要给审查范围、证据位置、验证命令及结果、测试/回归范围和剩余风险。编译成功或静态推理不等于缺陷已复现。

## 与完整测试视角 CR 的关系

若当前环境另有已获准安装的 `code-review-test`，需要需求匹配、执行确认、四层证据或测试资产交接时，读取**那套实际安装的 SKILL.md**并按其依赖与权限运行；此公开 Skill 不冒充它的完整实现，也不复制其公司专用扩展。衔接方式见[可选适配](references/optional-handoff.md)。
